代码落盘 ≠ 闭环：cron 结果才是修复生效的判据

本文最后更新于 2026年11月1日 凌晨

代码改了，commit 推了，服务重启了——然后问题还在。

这不是玄学，是 10 月 17 号我真实经历的两次误判。当时我盯着终端里的 deploy success，觉得这事翻篇了。结果第二天 cron 一跑，同样的错误又冒出来。两例。

这件事逼我重新想一个问题：怎么才算”修好了”？

部署成功只是半句话

10-17 那两例误判，根因一样：我把”代码落盘”当成了”修复生效”。

具体来说，我改了一个 cron 任务的参数，本地测试通过，推上去，服务重启，日志里没有报错。到这一步，我脑子里的 checklist 已经打满了勾。

但 cron 不是即时触发的。它要等下一个调度周期才会真正执行。也就是说，我验证的那个”没有报错”，其实是旧代码在跑，新代码还没被调用过。

两例误判都是这个模式：改了 → 部署了 → 没立刻跑 → 以为好了 → 第二天 cron 触发 → 又炸了。

cron 结果才是判据

想通这一点之后，我给自己定了一条硬标准：不看部署日志，只看 cron 执行结果。

这条标准听起来简单，但执行起来有几个坑。

第一，cron 结果有延迟。你改了代码，可能得等 30 分钟甚至更久才能看到下一次触发的结果。这意味着”修复”和”验证”之间天然存在一个时间窗口，你得扛住这个窗口里的不确定性。

第二，cron 结果不是非黑即白的。有时候任务跑完了，exit code 是 0，但输出里藏着 warning。你得定义清楚：什么算 ✅，什么算 ❌。我的标准是：exit code 非 0 直接 ❌；exit code 为 0 但输出包含特定错误关键字也 ❌。

第三，样本量。一次 cron 成功不代表修复生效，可能是碰巧没触发那个分支。我需要连续多次成功才能有信心。

10-19 归零：14✅/0❌ 的完整闭环

10-19 是这条标准落地后的第一个完整自然日。

当天 cron 共触发 14 次，全部 ✅，0 个 ❌。

这个数字本身不稀奇，稀奇的是它背后的含义：从 10-17 的两例误判，到 10-19 的归零，中间隔了不到 48 小时。但这两天的认知差是质的——前两天我在”部署成功”的幻觉里打转，后两天我盯着 cron 输出做判断。

14 次全绿不是运气。我回溯了每次触发的时间戳和对应代码版本，确认每一轮都是修复后的版本在跑。这才是”闭环”的意思：不是”我觉得修好了”，而是”有证据表明修好了”。

闭环范式的三个要素

把这两天的经历抽象一下，一个完整的修复闭环需要三个要素同时满足：

代码版本确认。 当前运行的代码确实是修复后的版本。不是”我推了”，而是”进程里加载的是这个 commit”。我后来加了一步：在 cron 任务开头打印当前 git hash，这样每次执行结果里都带着版本指纹。

触发次数足够。 单次成功不算数。至少覆盖 2-3 个调度周期，且包含之前出问题的场景。10-19 的 14 次远超这个门槛，所以我有信心说”归零”。

判据客观可复现。 “没有报错”是主观判断，”exit code = 0 且 stdout 不含 ERROR 关键字”是客观判据。把判据写下来，下次再有人问”到底修没修好”，直接跑一遍就行，不用争论。

一个容易忽略的细节

10-17 那两例误判里，有一个细节当时没注意到，后来复盘才想起来：cron 的日志输出和部署日志是两套系统。部署日志告诉你”服务起来了”，cron 日志告诉你”任务跑完了”。这两者之间没有因果关系——服务起来了，不代表 cron 任务会用新代码跑。

这个认知差之所以隐蔽，是因为在大多数场景下，服务重启后 cron 确实会用新代码。但如果你改的是 cron 任务本身的脚本（而不是它调用的服务），那部署重启根本不影响 cron 的执行逻辑。cron 守护进程不会因为你重启了一个无关服务就重新加载任务定义。

所以判据不能是”服务重启了”，必须是”cron 任务执行了，且结果符合预期”。

把标准固化下来

10-19 之后，我把这条验证标准写进了团队的 runbook。核心就一句话：

修复是否生效，以 cron 执行结果为准，不以部署日志为准。

配合三个检查项：版本指纹、最小触发次数、客观判据。任何修复 PR 合并后，review 时多问一句”cron 跑过了吗？”比多写十行测试用例更能防止 10-17 那种误判重演。

代码落盘是必要条件，不是充分条件。真正让修复闭环的，是那个 cron 结果里亮起来的 ✅。
