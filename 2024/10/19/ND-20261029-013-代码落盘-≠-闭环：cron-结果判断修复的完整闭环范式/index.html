代码落盘 ≠ 闭环：cron 结果判断修复的完整闭环范式

本文最后更新于 2026年10月29日 凌晨

代码改了，部署了，单测过了，线上跑了一夜——第二天早上看 cron 结果，还是红的。

10 月 17 号我经历了两次这种事。两次都是同一类问题：修复代码确实落盘了，但 cron 任务的结果判断逻辑没有跟着更新，导致”已修复”的 case 继续被标记为失败。两例误判，看着像修复没生效，其实修复生效了，是判断标准没对齐。

到 10 月 19 号，同样的流程跑了一天，14 个 cron 任务全部 ✅，0 个 ❌。从两例误判到归零，中间差的就是一个东西：用 cron 结果本身作为修复生效的验证标准。

代码落盘和闭环之间隔着什么

先说 10-17 那两例误判的具体过程。

第一次，凌晨 02:15 的 cron 任务报了失败。我查了日志，发现是上游接口返回了一个新的错误码，之前的修复逻辑只覆盖了旧错误码。我加了新错误码的处理，部署，跑了一次手动触发，返回 200，收工。

第二天早上看 cron 汇总，还是红的。

不是代码没部署上去。是 cron 结果判断脚本里，”成功”的定义是 HTTP 200 + body 里某个字段等于特定值。我手动触发时只看了 HTTP 状态码，没看 body 字段。代码确实生效了，但判断标准没满足，cron 结果还是失败。

第二次更隐蔽。一个数据同步任务，修复的是超时重试逻辑。我改了重试次数从 2 次到 5 次，部署，手动跑了一次，成功了。但 cron 结果判断里有一个”耗时 < 30s”的阈值，重试 5 次的时候耗时到了 42s，虽然最终成功了，但耗时超标，cron 还是判了失败。

两例误判的根因是同一个：我用了”手动触发成功”作为修复生效的标准，而不是用 cron 结果判断作为标准。

为什么手动触发不算数

手动触发和 cron 跑，看着是同一个脚本，实际上差异不小。

环境变量不同。cron 跑的时候用的是 crontab 里写死的环境变量，手动触发用的是我 shell 里的。比如 NODE_ENV，cron 里是 production，我手动跑的时候可能是 development，走的代码路径不一样。

超时配置不同。cron 任务有系统级的 timeout，我手动跑没有。10-17 第二次那个案例，如果 cron 的 timeout 是 30s，那重试 5 次根本跑不完，直接被 kill 了。

结果判断逻辑不同。cron 结果判断是独立于任务本身的，它有自己的成功/失败标准。任务自己返回 200 不代表 cron 判它成功。

所以”手动触发成功”只能证明代码逻辑本身没问题，不能证明在 cron 环境下也 OK。这两件事之间隔着的，就是上面那些差异。

10-19 归零是怎么做到的

10-18 我花了一天把 cron 结果判断的逻辑梳理了一遍，列出了所有 14 个 cron 任务的成功判断条件。不是”HTTP 200”这种笼统的，而是每个任务具体到字段级别的判断标准。

比如：

  • 任务 A：HTTP 200 + data.status === "completed" + data.recordCount > 0
  • 任务 B：HTTP 200 + 耗时 < 60s + 输出文件存在
  • 任务 C：进程退出码 0 + stdout 包含 “SUCCESS”

然后针对 10-17 那两例误判，做了两件事：

第一，把修复后的代码在 cron 环境下完整跑了一遍，不是手动触发，是等 cron 自然调度。确认 cron 结果判断给出的状态是 ✅。

第二，把”cron 结果判断条件”写进了修复 checklist。以后每次修 bug，部署完之后不是看”手动跑通没”，而是看”cron 结果判断条件满不满足”。

10-19 是第一个完整验证日。14 个 cron 任务从凌晨到深夜全部自然调度，每个任务的结果都经过了 cron 结果判断逻辑的处理。最终汇总：14 ✅，0 ❌。

这不是”没出问题”，是”出了问题能正确识别，没出错能正确判定为成功”。

验证标准怎么定

从这两次误判里提炼出来的验证标准，其实就一条：修复生效 = cron 结果判断给出 ✅，而不是任务本身跑通了。

具体操作层面：

  1. 修复部署后，等下一次 cron 自然调度（不要手动触发来验证）
  2. 看 cron 结果判断的输出，不是看任务日志
  3. 如果 cron 结果判断的条件本身有问题（比如阈值不合理），先修判断逻辑，再验证修复
  4. 连续观察 24 小时，确认全天 ✅

第 3 点容易被忽略。10-17 第一次误判，如果我只看任务日志，会觉得”代码没问题啊”，然后反复排查代码。但实际上问题出在判断标准上。判断标准本身可能是一个 bug——它定义了”什么算成功”，如果这个定义本身就不对，那任务跑了一百遍也是失败。

一个容易踩的坑

有人会说：”我手动触发的时候把环境变量设成和 cron 一样不就行了？”

理论上可以，实操中很难完全对齐。cron 的环境变量来自 crontab 文件 + 系统 profile，有些变量是动态计算的（比如 PATH 在不同 shell 下不一样）。你手动模拟的时候，总有某个变量对不上，然后你花两小时排查”为什么手动跑和 cron 跑结果不一样”，最后发现是 PATH 里多了个目录。

最省事的办法就是别模拟，等 cron 自己跑。慢是慢了点，但结果是最真实的。
