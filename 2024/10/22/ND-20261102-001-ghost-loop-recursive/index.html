幽灵闭环递归：日记 cron 连续两天执行但文件未生成

本文最后更新于 2026年11月2日 凌晨

10 月 22 号早上打开日记目录，10-20 和 10-21 的文件不在。

不是”可能不在”，是确定不在。ls 了一遍，10-19 的文件好好躺着，后面直接跳到 10-22（当天还没到生成时间）。连续两天，文件凭空消失了。

第一反应是 cron 没跑。翻 /var/log/cron，两条记录清清楚楚，10-20 和 10-21 各执行了一次，exit code 都是 0。

这就是”幽灵闭环”的意思——cron 认为任务完成了，脚本也认为自己跑完了，但产物就是没有。整个链路看起来是闭合的，实际是空的。

脚本跑了，但跑了个寂寞

先看脚本本身。日记生成逻辑很简单：从 SQLite 里查当天的记录，拼成 markdown，写到 ~/diary/2024-10-XX.md。

问题出在一个”优雅”的防御逻辑上：

如果当天没有记录，就打印一行 skip 然后正常退出。exit code 是 0，cron 日志里看起来一切正常。

但实际情况是：10-20 和 10-21 确实有记录。那为什么 query_day 返回了空？

答案藏在一个更隐蔽的地方——时区。

脚本里用 datetime.now() 取当前日期，但 cron 的执行环境里 TZ 变量没有被继承。服务器是 UTC，而我的记录是按北京时间存的。10 月 20 号北京时间 23:30 产生的记录，在 UTC 里已经是 10 月 21 号 07:30 了。

更关键的是，cron 的触发时间是每天 08:00（服务器时间）。08:00 UTC = 16:00 北京时间。datetime.now() 在 UTC 下返回的是 10-20，但数据库里 10-20 的北京时间记录，UTC 时间戳其实横跨了 10-19 和 10-20 两天。

查询条件 WHERE date(timestamp) = '2024-10-20' 在 UTC 下执行，漏掉了一批记录，同时也多捞了一批。最终结果是：某些天查出来是空的。

这不是一个”偶发”问题。它是时区不一致导致的确定性 bug，只是恰好 10-20 和 10-21 这两天触发了”空结果”的边界条件。

第一次修复：手动补跑 + 打日志

发现问题的当天下午，我做了三件事：

  1. 手动指定日期补跑了 10-20 和 10-21
  2. 在脚本里把 datetime.now() 改成 datetime.now(timezone(timedelta(hours=8)))
  3. 在 skip 分支里加了一行 print(f"[WARN] ...")，方便下次排查

这就是典型的”单次修复”。问题解决了，但我心里清楚，下次还会出类似的事。

因为整个系统里，”cron 执行成功”和”产物存在”之间没有任何关联。cron 只关心 exit code，脚本只关心自己有没有报错。没有人关心文件到底生成没有。

幽灵闭环的本质

把这件事抽象一下，结构是这样的：

  • 触发层：cron 按时触发，记录日志，exit code 0
  • 执行层：脚本运行，内部逻辑”正常”结束
  • 产物层：文件应该出现在某个路径

三层之间没有校验。触发层不知道产物层的状态，产物层也没有人去看。整个系统形成了一个”闭环”——但闭环里是空的。

我管这个叫”幽灵闭环递归”：每一层都认为自己完成了自己的职责，层层传递”一切正常”的信号，但最终的产物就是不存在。而且这个问题会递归地重复出现，因为没有任何机制会打断这个循环。

从单次修复到系统性校验

补跑之后我没急着收工。连续两天出事，说明这不是偶发，是结构性缺陷。

我加了两层校验：

第一层：脚本自检。 脚本执行完毕后，检查目标文件是否存在且非空。不存在就 exit 1。

这一层把”幽灵闭环”打断了。如果产物没出来，cron 日志里会留下 exit 1 的记录，下次翻日志就能发现。

第二层：独立巡检。 每天 09:00 跑一个独立的检查脚本，扫描过去 7 天的日记文件是否齐全。缺了就发一条通知。

这个巡检脚本跟生成脚本完全独立。即使生成脚本被误删、cron 配置被改掉、或者服务器重启后 cron 没恢复，巡检都能发现异常。

为什么不做得更复杂

你可能会问：为什么不直接上 Prometheus + Grafana，或者写个 systemd timer 替代 cron？

因为规模不匹配。一个每天生成一个 markdown 文件的小工具，上全套监控是杀鸡用牛刀。两层校验——脚本自检 + 独立巡检——已经覆盖了”产物缺失”这个核心风险，成本几乎为零。

但有一个原则我坚持了：校验必须独立于被校验的对象。 生成脚本自己说自己成功了不算数，必须有一个外部视角来确认产物真的存在。这就是巡检脚本存在的意义。

事后验证

加了校验之后又过了两周，10 月 28 号巡检脚本确实报警了一次——那天我出差，笔记本没开，cron 没跑。但这次 9:00 的通知让我 10 分钟就定位了原因，而不是像 10-22 号那样，两天之后才发现。

幽灵闭环被打破了。不是因为它不再出现，而是因为出现的时候，有人会在第一时间知道。
