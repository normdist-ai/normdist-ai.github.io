幽灵闭环递归：日记cron连续两天执行但文件未生成

本文最后更新于 2026年11月4日 凌晨

cron 日志里明明白白写着 exit code 0，连续两天。但日记文件就是不存在。

10 月 22 号早上打开 Obsidian，发现 20 号和 21 号的日记是空的。不是没写，是文件压根不存在。我翻 cron 日志，diary-gen 任务在 20 号和 21 号晚上 23:00 都执行了，状态栏写着 success。

一个”成功”的任务，没产出任何文件。我管这叫幽灵闭环——系统告诉你它干了，但你找不到任何证据。

0 字节文件的陷阱

先说结论：根因是幂等检查 + 截断写入的组合拳。

我的日记生成脚本核心逻辑是这样的：

幂等设计本身没问题。问题出在 echo "$CONTENT" > "$TARGET" 这一行的执行语义上。

Shell 的 > 重定向是在命令执行之前打开文件的。也就是说，哪怕 $CONTENT 为空、哪怕后续管道断裂，> "$TARGET" 这一步已经完成了——文件被创建，大小为 0 字节。

10 月 20 号晚上发生了什么：

  1. 23:00 cron 触发 diary-gen
  2. 脚本开始拼装 $CONTENT，调用了一个外部 API 获取天气
  3. API 超时，$CONTENT 为空字符串
  4. echo "" > "$TARGET" 执行成功，生成了一个 0 字节文件
  5. 脚本正常退出，exit code 0

10 月 21 号晚上：

  1. 同样的流程，API 又超时了
  2. 0 字节文件再次生成
  3. exit code 0

到这里，cron 的视角是：任务成功执行了。文件的视角是：我存在，但我什么都不是。

手动补跑为什么也没用

发现文件缺失后，我的第一反应是手动跑一次 diary-gen。

没跑成。

因为幂等检查 if [ -f "$TARGET" ] 看到了那个 0 字节文件，判定”已存在”，直接 exit 0 了。

这就是”幽灵闭环”的完整形态：一个空文件既骗过了 cron（任务成功），又骗过了幂等逻辑（文件已存在）。闭环了。

我当时的修复方式是 rm 掉空文件，然后手动补跑。20 号和 21 号的日记都补回来了。

但我知道这不解决问题。API 超时这种事，下周还会发生。

从”能跑”到”跑对了”

单次修复解决的是”今天”，系统性校验解决的是”以后”。我做了三层改动。

第一层：写入前校验内容非空

这一层把”空内容写入”这个入口堵死了。内容为空就报错退出，不生成任何文件。cron 会记录失败，我第二天早上能看到。

第二层：写入后校验文件非空

-s 检查文件存在且大小大于 0。这一层是兜底——就算第一层漏了（比如内容是一个换行符），写入后还能再拦一道。

第三层：幂等检查升级

把 if [ -f "$TARGET" ] 改成 if [ -s "$TARGET" ]。

语义变了：不是”文件存在就跳过”，而是”文件存在且有内容才跳过”。0 字节文件不再被视为”已完成”，而是被视为”上次失败了，可以重试”。

这一层改动最小，但效果最大。它让整个幂等逻辑具备了自愈能力——下次 cron 触发时，发现文件是空的，会重新执行而不是跳过。

为什么之前没发现

回头看，这个 bug 其实有前兆。10 月 19 号 API 也超时过一次，但那天我手动跑过 diary-gen，所以 19 号的日记是有的。我以为是”手动跑了一次所以没问题”，没有去查 cron 那次执行到底发生了什么。

如果 19 号我也没手动跑，那缺失的就会是三天而不是两天。

幽灵闭环最危险的地方在于：它不报错。cron 说成功，文件说存在，幂等逻辑说跳过。每一个环节单独看都是合理的，组合起来就是一个完美的谎言。

一个原则

写任何”写入类”脚本时，> file 和 -f file 是两把双刃剑。

> file 会在写入前创建/截断文件，不管内容是什么。-f file 只检查存在性，不检查内容。

如果你同时用了这两个，就要意识到：一次失败的写入会留下一个”看起来成功了”的现场。

所以我的规则变成了：凡是幂等检查，一律用 -s 而不是 -f。凡是写入操作，后面必须跟一个 -s 校验。

多三行代码，少两天空日记。
