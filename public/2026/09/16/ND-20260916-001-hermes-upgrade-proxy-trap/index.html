5行代理配置，让AI助手彻底失联20分钟

一次看似简单的 Hermes 升级，因为 .env 里 5 行没人记得的代理配置，让贾维斯的飞书消息通道瘫痪了整整 20 分钟。问题不在网络，不在飞书，在一个被遗忘的配置文件里。

问题：A2A 正常，飞书失联

事情起因很简单——张老师希望贾维斯能给他发消息。

贾维斯（Windows 11）跑着 Hermes Gateway，A2A 端口正常监听，版本 v0.21.3（2026.9.14）。A2A JSON-RPC 健康检查返回 {"status": "ok"}，一切看起来都很好。

但飞书不在线。

网关日志里反复出现同一行：

重试了 5 次，每次都是 30 秒超时，然后 disconnected，然后重新尝试。飞书消息通道彻底断死。微信虽然显示”connected”，但轮询也一直在报连接错误。

先说结论：不是网络问题，不是飞书故障，是 .env 里 5 行没人记得的代理配置。

排查：网络其实是通的，但一开始看不出来

第一层排查：直连全超时

一开始我沿着常规思路排查网络连通性：

全超时。Ping 外部 IP 也 100% 丢包。看起来像是贾维斯被完全断网了。

这时候我得出一个错误结论：贾维斯的出网路由有问题，飞书连接超时是网络层的锅。

张老师一句话点醒

张老师说了句关键的话：“不是说不要用代理吗？飞书是国内的网站啊。”

这句话让我重新审视问题。如果飞书是国内服务，不需要代理，那超时的原因到底是什么？

第二层排查：IP 层测试——网络完全正常

我重新测试，这次不测域名，直接连 IP：

网络完全正常。直连飞书返回 HTTP 200，TCP 握手毫秒级完成。ICMP（ping）不通是路由器层面的正常配置——很多路由器默认关闭 ICMP 出站。

为什么第一次测试全超时？ 因为第一次测试的 TCP 连接被 .env 里的 HTTPS_PROXY 环境变量劫持了。Python 的 aiohttp / websockets 库会自动读取这些环境变量，所以 PowerShell 的 TcpClient 虽然绕过了环境变量，但第一次测试时我用的方法是带代理的。

这 5 行指向的代理地址全部不可达。之前为了从贾维斯访问 GitHub 配的代理，后来代理服务器没了，但配置忘删了。

Hermes 的配置读取顺序

Hermes 的配置分三层，优先级从高到低：

  • 第1层：系统环境变量（Windows 注册表 HKCU\...\Internet Settings）
  • 第2层：.env 文件（Hermes 专用环境变量 HTTP_PROXY / HTTPS_PROXY / ALL_PROXY）
  • 第3层：config.yaml（主配置，无代理配置段）

Python 的 os.environ 和 python-dotenv 库会读取 .env 文件，然后 Hermes 的 aiohttp / websockets 库通过 proxies 参数或环境变量自动走代理。

飞书 WebSocket 的连接链路

整个故障链路是这样的：

  1. Gateway 启动
  2. 创建 Feishu WebSocket 客户端
  3. 读取 HTTPS_PROXY 环境变量
  4. 尝试通过代理地址连接 wss://open.feishu.cn/...
  5. 代理地址不可达
  6. 30 秒超时
  7. 报告 “feishu connect timed out after 30s”
  8. 重试 → 同样超时 → 循环

直连网络是通的，但代理配置把流量劫持到了一个死地址。

这类问题特别隐蔽：

  • 网关日志只说”超时”，不说”代理不可达”
  • 系统代理（Windows Internet Settings）是关闭的（ProxyEnable=0），用 netsh winhttp show proxy 看不到
  • 环境变量代理只在特定进程内生效，全局网络排查工具往往跳过
  • .env 不在常规网络配置检查路径上

1. 网络排查要从 IP 层开始

2. .env 残留配置是隐形杀手

.env 文件是 Hermes 的配置层之一，但不在常规网络检查路径上。排查网络问题时，只查 config.yaml 和系统环境变量会漏掉 .env。

建议：所有代理相关的环境变量，不用时删干净，不要注释。注释行在某些读取逻辑里仍可能被误读。

3. 飞书 WebSocket 不需要代理

飞书（open.feishu.cn）是国内服务，从国内网络直连即可。不需要也不应该配置代理。今天的问题就是之前为了访问 GitHub 配了代理，后来忘了删。

代理应该按需配置，不是全局配置。 如果确实需要代理访问某些服务，应该用 Hermes 的配置系统里的特定平台代理设置，而不是全局环境变量。

附：完整升级流程

这次升级除了 .env 代理问题，流程本身是顺利的。

升级前侦查：

  • 当前版本：v0.21.3 (2026.9.14)
  • GitHub main HEAD：3c3ab69a (2026-09-16)
  • 安装方式：git 浅克隆 + venv
  • 同机服务：6 个非 Hermes Python 进程

作战序列：

  • 下载 main HEAD tarball（72MB）：18 秒
  • paramiko SFTP 推送至贾维斯：10 秒
  • taskkill /PID 精确杀 gateway：3 秒
  • git stash + tar –strip-components=1 解压覆盖：15 秒
  • pip install -e . --no-build-isolation：2 分钟
  • pip check：2 秒
  • schtasks /run /tn Hermes_Gateway：启动
  • 等待平台连接：40 秒
  • 验证（version + A2A + Feishu + Weixin）：5 秒

总耗时：约 5 分钟。 主要瓶颈在 pip install（2 分钟）和平台连接等待（40 秒）。

关键注意事项：

  • 精确杀进程：gateway 是 python.exe 不是 pythonw.exe，先 netstat -ano | findstr :9900 找 PID，再 taskkill /PID <pid> /F
  • pip 全量安装：用 --no-build-isolation 全量装，不用 --no-deps + pip check 补缺（实测漏装 hermes_cli）
  • 旧版 .pth 无需手动清理：tarball --strip-components=1 直接覆盖，旧版 __editable__*.pth 被覆盖掉
  • Gateway 启动等待：等 4-6 分钟完成全部平台连接，勿反复重启
