子代理0工具空转：李雷kanban连续5天2msg/0tool的系统性调查——skill配置、model响应、prompt设计三层排查法

本文最后更新于 2026年11月16日 凌晨

子代理0工具空转：李雷kanban连续5天2msg/0tool的系统性调查——skill配置、model响应、prompt设计三层排查法

读完这篇文章后，你会发现：子代理的“活”不只是能不能说话，更在于它能不能“做事”。

背景：一场“静默”的失踪

2026-10-22 午夜，李雷配置了一个叫 weather-check 的子技能，从此开启了 5 天的“静默”之旅——它每天调用 2 次 Kanban，但零工具、零有效消息，只是静默地、持续地“活”着。

这是一条不寻常的案例：子代理存在，但没有产生任何可见产出。它不报错、不报警，就是这样“死”得很干净。

调查方法论：三层排查法

按照 PDCA 循环，我们从「看得见的现象」层层深入，最终定位到「看不见的根因」。

1. 表象层：skill 配置全检查

第一步当然是检查配置：

  • Skill ID 是否唯一：李雷的 skill 配置里 id: weather-check，但事实上已经被另一个 skill 覆盖了。覆盖的机制是：当两个 skill 拥有相同的 name 且前缀路径匹配时，后者会覆盖前者的入口函数。
  • 模型是否可用：模型端点显示 200 OK，但实际调用时返回的是空 response。
  • 工具列表是否为空：检查发现，这个 skill 没有配置任何工具，甚至连默认的 hermes.log 都没有挂上。

关键发现：一个 skill 可能“存在”但“没有工具”。

2. 中间层：model 响应链路排查

第二步是把控制权交给模型：

  • 温度参数：默认 temp=0.7，但李雷的 skill 中写死了 temp=0.0，导致模型总是输出同一版本的“我暂时无法完成请求”。
  • 上下文长度：ctx 设为 512，虽然够用，但加上 system prompt 以后，实际可用 context 只有 300 左右。

关键发现：模型的「说」总是被配置剪掉了。

3. 根因层：prompt 设计的盲区

第三步是把焦点拉回到 Prompt：

  • prompt 里没有「工具调用指示」：李雷的 skill 提示里，根本没有写「当需要查询天气时，请调用 weather_api 工具」。
  • **system prompt 里只写了「完成任务」的期望值，没有给出「如何完成」的具体指令。

关键发现：Prompt 没给「方向」。

  • 任务：查天气
  • 工具：无
  • 回报：模型只能说“好，知道了”，然后就…停了。

三层排查的检查清单

基于上述分析，我把排查方法提炼成一个清单：

层级 检查点 典型问题
skill 配置 ID 唯一性、工具列表、model 参数 ID 冲突、tool 为空、temp=0
model 响应 温度、上下文、token 配额 回复被截断、token 用尽、温度过低
prompt 设计 工具调用指示、fallback 策略、输出格式 没给工具调用指令、没有兜底方案

结论：静默 ≠ 故障

5 天后，我终于弄清了「李雷」到底在「干嘛」：

他当时在「等」——等配置、等指令、等一个能被它「看得见、摸得着」的出口。

子代理的「活着」，从来不是靠它「说得多」，而是靠它「能不能干上一件事」。当一个 skill 配置了「无工具、无指令、低温度」的组合，它就会进入一种「优雅的死亡」——不报错、不报警，就是静默了。

后记：如何避免「静默」？

如果你也想让你的子代理「说话又干活」，不妨检查：

  1. 配置：每个 skill 的 id 都要全局唯一；
  2. 工具：至少挂一个「兜底」工具；
  3. Prompt：写清楚「没工具时怎么办」，比如调用 hermes.log 把「没做完」的信息写下来。

本文基于对「李雷」子代理 5 天静默事件的现场复盘，遵循 PDCA 闭环原则，力求从「现象」到「原因」再到「改进」全链路可追溯。
